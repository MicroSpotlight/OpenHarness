# OpenHarness Agent Guide

This file defines the repository-wide working agreement for AI coding agents.
Follow more specific `AGENTS.md` files if they are added below a subdirectory.

## Project Intent

OpenHarness is a Tauri desktop host for the published `@deepseek-ai/dsh`
runtime. It packages the upstream server and Web UI into one native app while
preserving an independent OpenHarness product identity.

Keep changes in the repository that owns the behavior:

- Desktop lifecycle, native menus, tray behavior, runtime supervision, and the
  managed-runtime boundary belong here.
- Upstream runtime and Web UI behavior belongs in DeepSeek Harness unless a
  small compatibility patch is required for the packaged desktop app.
- Plugin discovery and installation policy belongs in
  `openharness-find-plugin`; catalog data belongs in `openharness-plugins`.

## Repository Map

- `src-tauri/`: Rust desktop host, Tauri configuration, permissions, and icons.
- `runtime/`: locked dependency manifest, OpenHarness patches, Native Bridge,
  and bundled package-manager launcher.
- `scripts/`: runtime assembly, branding, build, signing, and release helpers.
- `frontend/dist/`: minimal bootstrap page shown before the runtime is ready.
- `docs/`: public website and updater-manifest host.
- `.github/workflows/`: cross-platform release and Pages deployment workflows.

`src-tauri/runtime/` is generated by `scripts/setup-runtime.mjs` and ignored by
Git. Never edit or commit it as source.

## Toolchain And Commands

Required local tools are Rust, Bun, Node.js, and the platform prerequisites
listed in `README.md`.

```sh
bun install --frozen-lockfile
bun run setup:runtime
bun run dev
bun run build
```

Use these focused checks during development:

```sh
node --test scripts/*.test.mjs
cargo fmt --check --manifest-path src-tauri/Cargo.toml
cargo test --manifest-path src-tauri/Cargo.toml
git diff --check
```

Run the focused test for the code being changed first, then run the complete
JavaScript and Rust suites before a release. A packaging or platform-specific
change also requires the relevant Tauri build or CI job.

## Change Rules

- Read the surrounding implementation and preserve existing ownership
  boundaries before introducing a new abstraction.
- Keep dependency versions that are intentionally reproducible exact, and
  update their lockfiles in the same change.
- Do not hand-edit generated permissions, runtime bundles, build outputs, or
  release assets unless the generating workflow explicitly requires it.
- Keep Rust formatted with `cargo fmt`; keep JavaScript compatible with the
  repository's current Node/Bun runtime and existing module style.
- Add a regression test for behavior changes and bug fixes. Tests should assert
  externally meaningful behavior rather than implementation trivia.
- Preserve unrelated user changes in a dirty worktree. Do not use destructive
  Git commands or rewrite history without explicit authorization.
- Comments should explain constraints or non-obvious decisions, not narrate
  straightforward code.

## Desktop Runtime Invariants

- Bind the bundled server only to loopback and validate its reported URL before
  loading it.
- The Web UI belongs inside the Tauri WebView. Always launch upstream `dsh web`
  with `--no-open`; app startup must never open a system browser window.
- Let the operating system choose the local port (`--port 0`) to avoid port
  conflicts.
- Keep runtime telemetry disabled from the desktop launcher.
- Use the managed Node.js and pnpm paths for plugin operations. Do not silently
  depend on a user's global Node.js or package-manager installation.
- Preserve single-instance behavior, bounded restart backoff, child-process
  cleanup, and full process-tree cancellation.
- Treat the `web` profile and `~/.dsh` as user-owned persistent data. Tests and
  smoke checks must use an isolated temporary `DSH_HOME` and clean it up.
- Never log credentials, provider tokens, prompts, or other sensitive user
  content. Import only the environment variables already allowed by the host.

## Updating DeepSeek Harness

1. Review the upstream release notes and CLI help for behavioral or flag
   changes, not only API or type changes.
2. Update the exact `@deepseek-ai/dsh` version in `runtime/package.json` and
   regenerate `runtime/bun.lock` with Bun.
3. Rebuild or validate the managed runtime with `bun run setup:runtime`.
4. Verify OpenHarness branding, startup URL detection, Native Bridge loading,
   plugin discovery, and the no-external-browser invariant.
5. Run all JavaScript and Rust tests. For meaningful Web UI changes, perform an
   isolated real-runtime smoke test in addition to unit tests.
6. Commit only source manifests, lockfiles, patches, tests, and documentation;
   do not commit `src-tauri/runtime/`.

Prefer adapting the desktop launch contract to supported upstream flags. Keep
OpenHarness patches minimal, reviewable, and limited to desktop integration or
independent branding requirements.

## Release Contract

Only publish when the user explicitly authorizes a release.

- Confirm the working tree and intended commit before staging.
- Use conventional, scoped commit messages consistent with recent history.
- Never force-push shared branches or move an existing release tag.
- Release tags use valid SemVer with a `v` prefix, for example
  `v0.1.0-beta.9`. The tag's core version must match `package.json`,
  `src-tauri/Cargo.toml`, and `src-tauri/tauri.conf.json`.
- Push the commit before its annotated tag. A `v*` tag starts the desktop
  release workflow.
- Do not report success when the push succeeds but CI is still running. Verify
  all macOS, Windows, and Linux builds, the GitHub Release and required assets,
  and the Pages deployment of `latest.json`.

## Completion Report

State what changed, which checks ran, and whether any validation was skipped.
For releases, include the commit, tag, release URL, and final workflow status.
Call out residual platform risk directly rather than implying untested systems
were validated locally.
